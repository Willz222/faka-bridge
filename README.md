# Faka Bridge

用一套 Cloudflare Worker 代码桥接异次元发卡（ACG-Faka）与 Dujiao-Next。通过后台切换连接配置和商品映射，可同时支持：

- `Next → 异次元`：Next 作为下游，异次元作为上游。
- `Next → Next`：Dujiao-Next 作为下游和上游，Worker 负责隔离商品编号、重新定价、价保、幂等和发货回调。
- `异次元 → Next`：异次元作为下游，Next 作为上游；人工发货只在 Next 后台完成，随后自动回写异次元订单。
- `异次元 → 异次元`：异次元作为下游和上游；Worker 继续执行编号隔离、重新定价、价保和订单轮询。

| 下游 | 上游 | 商品同步 | 实时价保 | 下单与查单 | 发货回写 |
|---|---|---:|---:|---:|---:|
| Dujiao-Next | 异次元 | ✅ | ✅ | ✅ | ✅ |
| Dujiao-Next | Dujiao-Next | ✅ | ✅ | ✅ | ✅ |
| 异次元 | Dujiao-Next | ✅ | ✅ | ✅ | ✅ |
| 异次元 | 异次元 | ✅ | ✅ | ✅ | ✅ |

当前公开版本：`0.3.0`。它采用“单租户、多上游”模型：每个站长独立部署一套 Worker 和一套下游接入密钥，但可以在同一个后台添加多个异次元或 Dujiao-Next 上游。登录页与管理后台分离，管理后台采用浅色响应式界面。异次元共享 API 严格按官方文档执行：请求只提交 `app_id` 与 `sign`，`app_key` 仅在 Worker 内部生成签名，不发送给上游。

每个上游首次连接时读取一次完整候选目录，新发现商品默认不公开；管理员搜索并勾选需要上架的商品后，定时任务只刷新这些已勾选商品。未勾选的几百或几千个候选商品不会参与日常上游请求或商品写入。

## 设计原则

Worker 后台只负责连接配置、定价、同步、订单监控、重查和重发回调，不提供第二套人工发货入口。这样可以避免两边同时操作造成重复或错误发货。

下游接口只使用公开商品 ID、公开 SKU 和桥接订单号。上游域名、真实商品/SKU ID、上游订单号、密钥和错误原文均不会进入下游响应。配置密钥和待回调的交付内容使用 AES-GCM 加密后存入 D1；回调成功并超过保留期后自动清除交付密文。

## 功能

- 单文件 Cloudflare Worker，无前端构建依赖。
- Dujiao-Next Open API 兼容入口：`/api/v1/upstream/*`。
- 异次元共享店铺兼容入口：`/shared/*`。
- Next 发货回调入口：`/callbacks/next`。
- 独立管理员登录页：`/login`；浅色响应式管理后台：`/admin`。
- 异次元与 Dujiao-Next 商品自动同步、商品 ID 隔离映射、订单幂等、定时重查、回调重试。
- 四个桥接方向均在下单前实时读取上游成本与库存；超过安全涨价阈值、报价失败或库存不足时停止下单。
- 下单前先在 D1 原子占用下游订单号，防止并发重放造成重复上游订单。
- 多异次元 / 多 Next 上游连接；商品和订单按所属连接精确路由。
- 全局、单上游、单商品三级定价；支持百分比、固定金额、固定售价和最低售价。
- Cron 每 2 分钟进行轻量调度；只有存在到期订单或失败回调时才请求上游订单接口。商品价格与库存按每个上游设置的间隔刷新，下单前仍会实时核价。
- 上游提交结果不明确时进入“待人工核对”，系统不会自动重复购买；后台可接管已创建订单或确认未创建。
- 订单按状态、方向、上游和单号筛选，支持 CSV 导出，并按结算币种统计销售额、上游成本和毛利润。
- 商品列表和订单列表使用服务端分页，避免商品与订单增长后拖慢后台首页。
- 预占后未提交的超时订单会安全失败；已经提交但结果不明确的订单会自动转入待人工核对。
- 商品临时刷新失败会保留最近缓存，连续失败三次后才临时下架，恢复后自动重新上架。
- 上游余额检测、低余额 Telegram 提醒、运行环境就绪检查、脱敏配置导出和诊断报告。
- 审计日志、回调事件、价格历史和发货密文按保留天数分批清理，防止 D1 长期膨胀。
- Telegram 订单、价格变化、上游异常与恢复通知。
- 后台登录与桥接 API 持久化限流、签名会话、CSRF、严格 CSP。
- HTTPS 限制、私网目标拦截、Next 回调主机精确白名单。
- 异次元插件回调使用 HMAC-SHA256、时间窗和一次性 nonce。

## Cloudflare 部署（推荐）

需要 Node.js 20+、Cloudflare 账户以及 Wrangler 登录状态。

```bash
npm install
npx wrangler d1 create faka-bridge-db
```

把命令返回的 `database_id` 填入 `wrangler.jsonc`，然后初始化数据库。旧版升级也执行同一命令，它会依次应用尚未执行的迁移；`0005` 会保留全部历史订单并升级为四向订单结构，`0006` 会补充订单安全状态、固定上游归属、成本、余额和运维索引，`0007` 会增加公开 ID 防碰撞注册表和卡单恢复索引：

```bash
npm run db:remote
```

设置管理员账户以及三个 Worker Secret。不要把真实值写进 Git：

```bash
npx wrangler secret put ADMIN_USERNAME
npx wrangler secret put ADMIN_PASSWORD
npx wrangler secret put SESSION_SECRET
npx wrangler secret put MASTER_KEY
```

- `ADMIN_PASSWORD`：至少 12 位，建议使用密码管理器生成。
- `ADMIN_USERNAME`：可选环境变量；不设置时管理员账户默认为 `admin`，现有 `ADMIN_PASSWORD` 不变。
- `SESSION_SECRET`：至少 32 位随机值。
- `MASTER_KEY`：至少 32 位随机值；丢失后将无法解密已保存配置。
- 生产环境建议配置变量 `UPSTREAM_ALLOWED_HOSTS`：用逗号分隔允许访问的上游主机，例如 `upstream-a.example.com,upstream-b.example.com`。启用后，后台不能新增白名单外的连接。
- `SESSION_TTL_SECONDS`：后台登录有效期，默认 `28800` 秒；修改管理员账号或密码后，已有会话会立即失效。

部署并访问后台：

```bash
npm run deploy
```

打开 `https://你的-worker域名/login`，用管理员账户（默认 `admin`）和现有 `ADMIN_PASSWORD` 登录。建议再用 Cloudflare Access 限制 `/login*` 与 `/admin*` 只允许管理员身份访问。

### 使用 Cloudflare 网页控制台部署

如果不使用命令行，可以直接部署单文件版本：

1. 在 Cloudflare 创建 Worker，并把 [`release/faka-bridge-worker-v0.3.0.txt`](release/faka-bridge-worker-v0.3.0.txt) 的全部内容复制到代码编辑器。
2. 在 Worker 的“绑定”中添加 D1 数据库绑定，变量名必须是 `DB`。
3. 新建 D1 数据库后，在 D1 控制台按编号顺序执行 `migrations/0001` 到 `0007`；从 `0.2.0` 升级只执行 `migrations/0007_v030_reliability.sql`。绝对不要重复执行带有 `ALTER TABLE` 的旧迁移。
4. 在 Worker“变量和机密”中添加 `ADMIN_USERNAME`、`ADMIN_PASSWORD`、`SESSION_SECRET`、`MASTER_KEY`。其中后三项必须设为加密机密；`ADMIN_PASSWORD` 至少 12 位，另外两个至少 32 位。
5. 添加 Cron 触发器 `*/2 * * * *`，然后部署 Worker。
6. 打开 `/health`，确认返回 `ok: true` 且版本为 `0.3.0`；再登录后台执行“检查运行环境”，确认数据库和必要变量正常。

## 后台配置顺序

1. 在“上游连接”中逐个添加异次元或 Next 的 HTTPS 地址和上游凭据；保存后 Worker 会在后台读取一次完整候选目录。
2. 打开“商品与定价 → 管理上架商品”，选择上游、搜索并勾选真正要提供给下游的商品，然后保存。
3. 在“通知与系统”设置全局加价；需要时再给某个上游或商品设置覆盖策略。
4. 生成“异次元接入密钥”和“Next 接入密钥”，立即复制到相应下游平台。
5. 生成“插件回调密钥”，安装下方异次元插件并填入同一密钥。
6. 填写异次元插件回调地址，以及允许接收回调的 Next 下游主机名。
7. 可选：配置 Telegram Bot Token 与 Chat ID，保存后发送测试消息。
8. 日常只需点击“刷新已上架商品”；仅在要寻找新商品时使用“强制刷新完整商品库”。

上游连接的状态规则：新建连接保存成功后会立即读取完整候选目录；点击“停用”后，该连接立即显示“已停用”，对应商品停止对外提供并退出商品刷新任务，但已有订单仍会继续查询和处理发货回调；点击“启用”后，Worker 会马上刷新此前已勾选的商品。只有已停用的连接才显示“删除”；删除会清除其凭据、定价规则和商品映射，且不可恢复。为保证历史订单重查和人工发货回调安全，只要该上游已经产生桥接订单，后台就会拒绝删除，此时应保持“已停用”。

秘密输入框留空代表保留原值。重新生成接入密钥会让旧密钥立即失效。

## 方向一：Next 对接异次元

在 Next 新建上游连接时使用：

- Base URL：`https://你的-worker域名`
- API Key：后台生成的 `inbound_next_api_key`
- API Secret：后台同时生成的 `inbound_next_api_secret`

这两个值不同，必须分别完整复制，不能互换。

Worker 使用后台保存的多个异次元 App ID / App Key 分别拉取目录。Next 打开“从上游导入商品”时即可直接看到合并后的商品；公开商品 ID 会包含不可逆的连接隔离，不会和其他上游冲突。订单创建和查询始终回到该商品所属的异次元连接。

## 方向二：Next 对接 Next

下游 Next 的连接方法与上一节相同，仍然填写 Worker 的 Base URL、`inbound_next_api_key` 和 `inbound_next_api_secret`。Worker 会把所有启用中的异次元和 Next 上游商品合并为一个目录；下游导入 Next 上游商品后，下单会自动路由到该商品所属的 Next 连接。

这个方向不是透明转发：公开商品/SKU ID、售价、库存和订单号仍由 Worker 隔离；下单前仍执行实时价格与库存保护；上游 Next 发货后先回调 Worker，再由 Worker 使用下游提供的回调地址通知下游 Next。

在下游 Next 新建“连接 Worker”的上游连接时，回调 URL 必须指向**下游 Next 自己的 API 回调入口**：

```text
https://你的下游-Next-API域名/api/v1/upstream/callback
```

不要填写 Worker 的 `/api/v1/upstream/callback`，也不要只照搬界面中的 `/callback` 占位文字。Worker 后台“允许回调的 Next 主机”填写上述 URL 的主机名，例如 `shop.example.com`，不要包含协议和路径。修改回调 URL 只影响修改后新建的订单；旧订单会继续使用创建时保存的回调地址。

Worker 作为 Next 上游的 Base URL 与回调 URL 是两个不同方向：

- Base URL：`https://你的-worker域名`
- 回调 URL：`https://你的下游-Next-API域名/api/v1/upstream/callback`

## 定价、同步与健康检测

定价优先级从高到低为：单商品、单上游、全局。策略含义：

- 百分比：`售价 = 成本 × (1 + 百分比 / 100)`。
- 固定金额：`售价 = 成本 + 固定金额`。
- 固定售价：直接使用填写的售价。
- 不加价：售价等于成本。
- 最低售价：在以上结果之上再应用价格下限。

“通知与系统”中的下单价格保护同时作用于全部四个方向：

- 默认启用，并在真正创建上游订单前实时询价和检查库存。
- “允许成本涨幅”以商品上次同步成本为基准；`0%` 表示成本一上涨就阻止订单。
- 即使允许涨幅较大，上游总成本也不能高于本次下游售价，避免倒贴成交。
- 实时报价失败、过期、库存不足或数量超限时采用失败关闭策略，不会用旧缓存继续下单。
- 价格保护只保证创建上游订单前最后一次可见报价；如果上游在询价后、扣款时再次瞬时改价，Worker 会记录并通知，但最终仍取决于上游是否提供带价格锁定的下单接口。

Cloudflare Cron 触发器当前每 2 分钟唤醒一次，但并不代表每次都会请求所有上游。每次唤醒先读取轻量工作计数：没有到期待发货订单时不请求上游订单接口，没有失败回调时不发送回调；只在某个上游到达自己的商品刷新间隔时读取该连接中已勾选且仍有效的商品。健康与余额检测最多每 30 分钟一次，过期数据清理最多每天一次。完整候选目录不会被 Cron 反复读取，只有新增连接或管理员点击“强制刷新完整商品库”时才扫描。数据完全相同时不会写商品映射，也不会扫描整张 Next 目录缓存表。某个已勾选商品实时刷新失败时会暂时下架，后续成功后自动恢复，避免把无法核价的旧缓存继续提供给下游。

D1 只保存必须可靠持久化的数据：配置、商品映射、订单、价格变化和回调状态。Next 商品目录采用数据库内分页并叠加 30 秒边缘缓存；短期配置缓存、普通目录请求限流和稳定状态心跳不会持续写入 D1。关键下单接口优先使用 `ORDER_RATE_LIMITER` 全局限流绑定；直接粘贴单文件但未添加此绑定时，自动回退到 D1 持久化限流，安全性不降级但会增加少量订单级写入。对当前单租户规模不建议把整套数据改到外部数据库；D1 与 Worker 同平台，部署和故障面最小。若未来升级为多租户并达到每日数百万订单查询，再评估 PostgreSQL + Hyperdrive，或把仅用于展示的商品缓存迁移到 KV，同时继续把订单幂等数据保留在强一致存储中。

Telegram 消息只包含后台显示名称、桥接单号、公开商品信息、价格差异和通用状态；不会包含 Bot Token、上游地址、上游真实商品/订单编号、客户联系方式或卡密。

## 方向三：异次元对接 Next

在异次元新增原生共享店铺时使用：

- 店铺地址：`https://你的-worker域名`
- App ID：后台生成的 `inbound_acg_app_id`
- App Key：后台生成的 `inbound_acg_app_key`

该方向的商品会从所有启用的 Next 上游自动同步。异次元下单后，Worker 在对应 Next 上游创建订单；管理员在 Next 后台人工发货；Next 回调 Worker；Worker 再签名回调异次元插件更新卡密。标准商品目录接口不可用的上游需要先修复或升级接口，不再通过手工映射绕过目录校验。

### 安装异次元回调插件

插件文件位于 [`acg-plugin`](acg-plugin/README.md)。按其中说明复制 Controller、复制配置、导入 SQL。Worker 后台回调地址填写：

```text
https://你的异次元域名/shared/nextBridgeCallback/deliver
```

异次元当前的共享商品流程会在上游下单响应后把订单标记为已处理，因此等待人工发货期间会先显示“订单待处理，请稍后查询”；插件回调到达后会用真实发货内容覆盖。这里不返回 Next 的域名、订单号或错误详情。

## 方向四：异次元对接异次元

下游异次元的连接方法与“方向三”相同，仍填写 Worker 地址和后台生成的 `inbound_acg_app_id` / `inbound_acg_app_key`。在“管理上架商品”勾选异次元上游商品后，它会同时出现在 Next 和异次元两种下游目录中；异次元下游下单时，Worker 自动向该商品所属的异次元上游实时询价并创建订单。即时发货直接返回；延迟发货通过定时查询取得后，再使用同一异次元回调插件更新下游订单。

## 本地开发与测试

复制 `.dev.vars.example` 为 `.dev.vars`，只在本地填写随机秘密，然后运行：

```bash
npm run db:local
npm run dev
npm test
```

健康检查：`GET /health`。

## 安全注意事项

- 生产环境必须使用 HTTPS，不要关闭签名或回调白名单。
- `MASTER_KEY` 仅存 Cloudflare Secret；D1 备份不包含可直接使用的明文凭据。
- 不要把上游真实 ID 放进“公开 ID”字段。
- 回调白名单必须写明确域名，不支持通配符。
- 日志只记录内部错误代码，不记录密钥、卡密或上游响应正文。
- 发布前请在测试商品上完整走通下单、人工发货、回调和重发流程。
